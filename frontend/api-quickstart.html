01Overview

The DojangScore API is a thin, authenticated read-layer over the DojangScoreV2 contract on GIWA. It converts on-chain attestations (Upbit KYC via Dojang, verified balance, account age, verified code) plus on-chain behaviour into a single 0–1000 trust score with a tier and a provenance ceiling.

Use it to gate, weight, or price anything off-chain: launchpad allocations, airdrop multipliers, trading fees, remittance limits, quest rewards. For settlement-critical logic, read the contract on-chain instead (see On-chain vs API).

Design principle: the API never invents trust. Every point it returns is traceable to a provenance class, and the score can never exceed the ceiling set by the strongest proof a wallet holds.

WHY PROVEN?

The Trust Layer

Activity can be faked. Identity can't.
01

Identity, not just activity.

Volume is cheap — bots can fake a million swaps. Proven scores who you are, not just what you do: we read Dojang attestations (Upbit KYC, verified balance, account age, verified code) via EAS and compress them into one 0–1000 trust score. Activity can raise your score; it can never substitute for proof.

—Activity-only scorers (e.g. Hanok) reward wash-trading. Proven rewards being a provable human.
02

The Provenance Ceiling.

Our unique cryptographic guarantee: a score can never exceed the strength of its strongest underlying proof. Behavioral points grind you to Silver; consented proofs open Gold; only a regulated attester root unlocks Platinum. A farm with infinite volume still caps at Silver — the ceiling is enforced on-chain, not by policy.

—No other scoring system on GIWA — including Hanok — has a ceiling. Ours is math.
03

Regulatory ready.

Because Proven integrates with Dojang and Upbit KYC, the Platinum tier is compliant-ready for B2B and institutional flows. Remittance limits, tiered fees, gated allocations — every gate inherits a KYC-backed attestation, not a heuristic.

—Institutions don't buy heuristics. They buy attestations.

03Authentication

Every request requires the x-proven-key header. Missing or invalid keys return 401.

HeaderTypeDescription
x-proven-keystringYour issued API key. Keep it server-side; never ship it in client bundles.
Security: keys identify your project for quota + billing. If a key leaks, rotate it by requesting a re-issue; the old key is invalidated on next deploy.

Responses include rate-limit headers (X-RateLimit-Limit, -Remaining, -Reset) so you can throttle client-side. See Rate limits.

08Playbooks

Drop-in gating patterns. Each is a few lines because the hard part (provenance) is already on-chain.

Launchpad · sybil-resistant allocation

// Only wallets with a real proof get an allocation; weight by tier.
const s = await score(addr);
if (s.ceilingProvenance === "NONE")        reject();          // no proof, no alloc
const mult = [0, 1, 1.5, 2][s.tier];       // Standard..Platinum
alloc = base * mult;

Airdrop · tier multipliers

const MULT = { Standard:1, Silver:1.25, Gold:1.5, Platinum:2 };
payout = base * MULT[s.tierName];

Payments / remittance · tiered limits

const DAILY = { Standard:500, Silver:2500, Gold:10000, Platinum:50000 };
limit = DAILY[s.tierName];

Quests · gate high-value tasks

if (s.tier >= 1) unlock("high-value quest");  // Silver+
